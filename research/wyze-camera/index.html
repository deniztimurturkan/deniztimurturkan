Reverse engineering the Wyze camera's RF protocol

How our team decoded a proprietary sensor radio protocol from firmware, and showed that the camera system accepts replayed sensor packets and unsigned firmware.

Read the paper (PDF) ↗ ESCS publications page ↗
Role
Subteam co-lead (team of 8)
Timeline
Aug 2023 – May 2025
Device
Wyze Cam V2 + sensors
Tools
Ghidra, J-Link, GNU Radio, USRP N210, URH, Scapy

The question

Wyze cameras are popular in homes and small businesses, and they have a history of security problems, including an authentication bypass (CVE-2019-9564) and a stack buffer overflow leading to remote code execution (CVE-2019-12266). Our team wanted to look at a less-studied part of the system: the wireless link between the camera and its motion and contact sensors.

The long-term goal was to reverse engineer that radio protocol by hand, then try to reach the same results with RF fuzzing, to see whether fuzzing is a practical alternative to manual reverse engineering for RF devices.

The system

The Wyze Cam V2 kit has four boards:

  • Contact and motion sensors: each uses a TI CC1310 microcontroller and sends a packet over RF when its magnetic switch or PIR sensor changes state.
  • Sensor bridge: a CC1310 running Wyze's proprietary firmware. It receives sensor traffic and passes it to the camera over USB. This firmware was our main target.
  • Camera mainboard: an Ingenic T20 MIPS processor running embedded Linux, which relays events to the Wyze cloud and app. We got root by soldering headers onto an open serial port and cracking the root password.

Decoding the packet format

The CC1310 supports several standard radio modes, but Wyze uses its proprietary mode. Working from TI's technical reference manual and SDK samples, we matched SDK structures such as rfc_CMD_PROP_TX_ADV_s to the disassembled bridge firmware in Ghidra. That let us find and label the functions behind RF setup, the receive queue, and packet processing, and recover the on-air packet layout:

Sync word0x5555904E
Header16 bits
Payload3 bytes
CRCintegrity check

Wyze sensor packet as recovered from firmware. The CRC covers the payload but not the sync word or header.

From static to live analysis

Static analysis only goes so far, so we moved to stepping through the bridge's packet-processing routine while it ran. We started with Ghidra's debugger, then switched to J-Link on a remote test bed, where we could write directly to the device's memory and registers while it handled real traffic. That showed us how the routine checks radio status (PROP_DONE_OK), reads the 2-byte header (bits 0–10 hold the length, bit 11 the whitening flag, bit 12 the CRC length), and uses individual bits in the first payload bytes as flags that steer control flow. Knowing those bits is what makes it possible to craft packets that drive the device in specific, controlled ways.

What we found

  • Replay attack. We captured sensor traffic with GNU Radio and replayed it to the sensor bridge with an Ettus USRP N210. The bridge acknowledged the replayed packets as genuine. The sensor's 16-bit event counter didn't help, because a replayed packet simply carries the counter value it was captured with. We used Universal Radio Hacker to modulate and send arbitrary packets.
  • Unsigned firmware. We modified the stock camera firmware and installed it on the device, which shows Wyze doesn't sign its firmware. That's another way around the system's security controls.

My part

As subteam co-lead, I ran our check-in meetings and kept the presentations and the paper on schedule. On the technical side, I worked on static and dynamic analysis of the bridge firmware in Ghidra, on RF analysis of both transmit and receive, and on SDR spoofing tools written in Scapy to simulate the sensors and test how the bridge handles crafted traffic.

What's next

The research continues with a testbed for RF fuzzing: sending malformed packets to the bridge and comparing what fuzzing uncovers with what we found by hand.
